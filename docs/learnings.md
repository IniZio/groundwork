# Learnings

- **Agent skill invocation is partially advisory**: After adding "MANDATORY SKILL INVOCATION" rules with `invoke skill "name"` syntax to the bootstrap, the agent loads `diagnose` for standard bugs (confirmed 3/3 runs) and `interview` for features/small changes (confirmed 2/2 runs after tightening trivial criteria). The key insight: the "Trivial small change" escape hatch was too broad — the agent re-classified everything as trivial. Fix: tightened criteria to ≤1 file, ≤10 lines, no new behavior. Multi-file changes or new user-facing behavior must go through interview.
- **ACP server must run via PTY**: `opencode acp` backgrounded from bash dies silently. Must start via `pty_spawn` for the process to survive. The `acp-harness.sh` `start` command has this limitation documented.
- **Test project pollution**: ACP tests that implement features (dark mode, toggle-all) permanently modify the test project. Tests must either: (a) recreate the project before each run, or (b) use `git stash`/`git checkout` to reset between tests. Otherwise, subsequent tests find existing implementations and classify as trivial.
- **Progressive disclosure routing**: Replaced strict classification-based routing with progressive disclosure — bugs always get `diagnose`, changes default to direct implementation, and escalation signals (multi-file, ambiguity, ≥1d scope) trigger `interview` on demand. This eliminates the "trivial escape hatch" problem because there's no special trivial category to abuse — direct implementation IS the default. 3 skipped ACP tests were unskipped and updated to match this new model. The key insight: don't fight the agent's natural tendency to implement directly — embrace it as the default and escalate only when specific signals are present.
- **`pnpm run check` bundles codegen-check with repo-wide tsc**: In the groundwork plugin, `check` = `check:agents && tsc --noEmit`. The `check:agents` half (codegen sync) can pass cleanly while the `tsc --noEmit` half fails on pre-existing baseline errors in unrelated files (e.g. missing `@opencode-ai/plugin` dep). For codegen-only work, verify with `pnpm run check:agents` and confirm zero tsc errors land in your own files via `npx tsc --noEmit 2>&1 | grep "<your-files>"` — don't assume a red `check` means your change broke anything.
- **Completion gate file has lifecycle gaps**: The `.groundwork/gate-approved` timestamp file (written on APPROVE, removed on GAPS/CORRECTION/STOP) has four known limitations: (1) no expiry — a stale approval from a prior task persists and could let a future task skip its gate; (2) no per-task scoping — the file is global to the directory, so concurrent tasks share gate state; (3) broad question warning — the `tool.execute.before` warning fires on ALL `question` calls when no gate file exists, including mid-task clarifications, which may train users to ignore it; (4) substring matching — APPROVE detection uses `includes('approve')` on stringified output, risking false positives if "approve" appears in a non-gate context or false negatives if the result structure differs from expected.
- **opencode loads plugins from a snapshot cache, NOT the live source — edits to plugin source are invisible until the cache is synced**: opencode resolves each `plugin` entry (incl. local-path like `"./plugins/groundwork"`), reads its `package.json`, and loads from a cached snapshot at `~/.claude/plugins/cache/<source>/<name>/<version>/` (e.g. `cache/groundwork/groundwork/2.2.0/`). It does **NOT** refresh this cache on server boot (proven: a post-edit boot left the cached `groundwork.js` byte-for-byte identical, mtime unchanged) and it does **NOT** re-snapshot when the live source changes. The `opencode plugin <path> --force` CLI only updates the config entry — it does **NOT** re-copy/refresh same-version cache files (proven: with the cache slot removed, `--force` reported "Installed/Done" but recreated nothing). VERIFIED workaround: after editing plugin source, copy the changed files into the cache slot (`cp <live> ~/.claude/plugins/cache/<...>/<version>/<same-rel-path>`); the cache must also contain the deps the file imports (e.g. `src/lib/goal.ts`, `.opencode/node_modules/@opencode-ai/plugin`). LIKELY fresh-re-snapshot trigger (unverified): bump `package.json` `version` so a new slot is created on next boot. NOTE: skills load LIVE from the source dir (`~/.claude/plugins/groundwork/skills/`) via a SEPARATE mechanism — so skill edits appear immediately but tool-registering JS (`groundwork.js`) does not. opencode is a Bun-embedded Go binary, so `.js` specifiers resolve to `.ts` source natively (no precompile needed).
